1.0요약

sessionhub는 지금 세 가지 일을 한다 — 모든 머신의 세션을 한 곳으로 미러링하고, 세션마다 한 줄로 요약(인덱싱)하고, 그 요약을 전문 검색한다. 문제는 첫 단계다. 원본을 100% 통째로 복사해 이고 다닌다.

실측 결과 그 원본의 0.3%만이 사람과 모델이 실제로 주고받은 말이고, 나머지 99.7%는 도구 실행 로그·스트리밍 프레임·토큰 usage다. 검색은 이미 80MB짜리 인덱스로 되고, 원본은 오직 "그때 뭐라 했더라"를 다시 읽을 때만 쓰인다. 그 만일을 위해 10GB를 영구 보관하고 있다.

Decision · 결정 미러를 폐기한다. 원본 로그는 각 머신의 원래 자리에 그대로 두고, 허브는 (1) 검색 인덱스와 (2) 대화만 정제한 가벼운 digest를 갖는다. 원문 전체가 필요하면 그때 원위치를 열거나 ssh로 당긴다. 10.1GB → 약 380MB (26배 감소).

2.0지금 구조 — 이놈이 뭐 하는 놈인가

데이터가 어디서 와서 어디로 가는지, 어느 단계에서 트림되는지를 한 장으로.

Answer · 세 질문에 대한 답 다 백업해서 가져오나? — raw 층은 그렇다(원본 100%). 이게 10GB의 정체.
트림하나? — DB 층만 그렇다. raw는 트림 안 한다. ← 여기가 불일치.
검색 잘 되게 하나? — 그렇다(FTS5). 단 검색되는 건 요약본뿐.

3.0트림 로직 — 지금 무엇을, 어떻게 버리는가

현재 트림은 전부 어댑터의 parse() 안에 휴리스틱으로 들어있다. 원본을 한 줄씩 읽으며 필요한 필드만 뽑아내고 나머지는 자연히 버려진다.

3.1  무엇을 남기나

남기는 것규칙버리는 것
제목첫 user 메시지를 120자로 컷이후 모든 대화
첫 발화 원문같은 메시지를 500자로 컷500자 초과분
파일 목록tool_use의 file_path/path 추출, 최대 20개cd/ls/git/npm/cat·http·/dev·/tmp
메타project·machine·시각·토큰 합계턴별 토큰·캐시·모델 파라미터

3.2  세션 자체를 버리는 기준

  • 메시지 2개 미만 → parse()가 None 반환, 통째 폐기
  • 제목이 "SYSTEM"으로 시작 → (agent session)으로 대체 표기
  • subagent / exec → 저장은 하되 기본 조회에서 숨김(-a로 노출)

3.3  구현됐지만 비어있는 것

Constraint · 현황 스키마에 llm_summary·why_started 컬럼이 있으나 채우는 코드가 없어 7,424건 전부 비어있다. "원문 대신 요약을 저장한다"는 설계 의도는 있었으나 절반만 구현됐다 — DB 인덱스는 트림하고, raw 미러는 트림하지 않는 지금의 불일치가 여기서 나온다.

4.0측정 — 왜 10GB인가

macpro·mini·로컬에서 40개 파일을 무작위 표본으로 바이트 구성을 쟀다.

# 원본 JSONL 바이트 구성 (표본 37.6 MB)
progress          39.0%  ┐
response_item     31.2%  ├─ 도구 실행 · 스트리밍 로그. 사람이 다시 볼 일 없음
event_msg         11.1%  ┘
user              10.7%  ┐
assistant          2.4%  ┴─ 실제 대화 (이 중 텍스트만 치면 전체의 0.3%)
session_meta       0.8%
turn_context       0.5%
attachment         0.5%

# 결론
원본의 99.7%가 검색에도, 사람의 재열람에도 안 쓰이는 잡음.
그걸 이고 다니는 게 10 GB의 실체다.

5.0제안 아키텍처 — 3층으로 이름 붙이기

멘탈모델의 핵심은 이름이다. 지금은 "raw / hub.db" 2층인데 이름이 역할을 안 드러낸다. 세 층으로 재정의하고, 각 층의 소유·수명·크기를 못박는다.

┌─ MIRROR ── 각 머신의 원본. sessionhub는 소유하지 않는다. ──────────┐
│   위치   ~/.claude · ~/.codex  (원래 자리, 그대로)                       │
│   수명   에이전트가 관리 (sessionhub는 건드리지 않음)                    │
│   크기   허브에 0 — 더 이상 복사해 쌓지 않는다                        │
└──────────────────────────────┬───────────────────────────────────────┘
                               │  parse() — 대화 텍스트만 추출
                               ▼
┌─ DIGEST ── 세션당 정제 대화. 원문 재열람은 이걸로 대체. ───────────────┐
│   내용   user·assistant의 text만. tool_use·progress·usage 제거      │
│   형태   digests/<host>/<id>.txt.zst  (zstd 압축, 세션당 수 KB)          │
│   크기   ~300 MB  (원본의 약 3%, 압축 후)                             │
└──────────────────────────────┬───────────────────────────────────────┘
                               │  인덱싱
                               ▼
┌─ INDEX ── hub.db. 검색·목록·메타. 지금 그대로 (이미 잘 트림됨). ───────┐
│   내용   세션당 요약 1행 + FTS5 + MIRROR 원위치 절대경로              │
│   크기   80 MB                                                       │
└───────────────────────────────────────────────────────────────────────┘

INDEX는 각 세션이 원래 어느 머신 어느 경로에서 왔는지(origin_host + origin_path)를 이미 안다. sessionhub raw는 먼저 DIGEST를 보여주고, 원문 전체가 필요하면 그 원위치를 안내하거나 ssh로 그때 당긴다. 미러를 상시 보관할 이유가 사라진다.

6.0옵션 정리 — 원문을 어떻게 다룰 것인가

축은 하나다: "원문 전체를 다시 볼 필요가 생겼을 때, 그것을 어디서 가져오는가." 네 가지 답이 있고, 크기·오프라인 가용성·복잡도가 맞교환된다.

옵션원문 소재허브 크기오프라인 원문판정
A · 현행 유지미러 (허브에 100% 복사)10.1 GB항상 가능기각 — 용량이 운영을 잠식
B · 정제본 + 원위치 참조MIRROR는 각 머신 원위치, 허브엔 DIGEST~380 MB정제본은 가능, 전문은 ssh채택 — 아래 근거
C · 인덱스만각 머신 원위치 (허브엔 요약만)80 MB불가 (요약만)대안 — 가장 가벼우나 재열람이 빈약
D · 정제본 + 미러 유지양쪽 다 보관~10.4 GB항상 가능기각 — 무거움을 안 푼다
Decision · 왜 B인가 C는 너무 적게 남기고, A·D는 너무 많이 이고 간다. B는 실제로 쓰이는 0.3%(대화)를 압축해 허브에 두어 "그때 뭐라 했더라"를 오프라인에서도 즉답하고, 그 밖의 로그 전문은 원본이 살아있는 각 머신에 위임한다. 원문은 어차피 에이전트가 원위치에 갖고 있으므로 이중 보관은 순수 낭비다. INDEX가 원위치 경로를 기록하니 필요할 때 정확히 찾아간다.

6.1  B를 뒷받침하는 사실

  • 원문은 사라지지 않는다 — 각 머신의 ~/.claude·~/.codex에 그대로 있다. 허브가 복사본을 버려도 원본은 무사.
  • 재열람의 90%는 대화면 충분 — 실측상 사람이 다시 찾는 건 "무슨 말을 했나"지 tool_use diff 전문이 아니다. 그건 DIGEST가 담는다.
  • 원위치 참조가 이미 가능 — INDEX에 machine과 원본 경로가 있다. origin_host 한 컬럼만 추가하면 ssh <host> less <path>로 전문에 닿는다.

7.0옵션성 — 무엇을 설정 가능하게 두는가

기본값으로 옳은 일을 하되, 취향과 환경 차이를 두 개의 노브로만 연다. 노브가 많으면 멘탈모델이 흐려진다 — 이 도구의 "인덱스는 작게" 철학과 어긋난다.

7.1  노출하는 노브 (2개)

설정값의미기본
digest.modeconversation사람+모델 발화 텍스트만 (권장)기본값
fulltool 호출·파일 diff 요약까지 포함 (더 큼)
noneDIGEST 안 만듦 = 옵션 C (가장 가벼움)
keep_mirrorfalse정제 후 미러 삭제 = 옵션 B (권장)기본값
true원본 미러 상시 보관 = 옵션 A (오프라인 전문 필요시)

두 노브의 조합이 곧 4옵션이다: conversation·false=B(기본), none·false=C, *·true=A/D. 사용자는 "옵션 A/B/C/D"를 외울 필요 없이 "정제 강도"와 "원본 보관 여부"만 고르면 된다.

7.2  일부러 노브로 만들지 않는 것

Constraint · 고정 결정 컷 길이(제목 120·발화 500), 파일 추출 휴리스틱, 세션 폐기 기준(2메시지 미만)은 설정으로 열지 않는다. 이것들은 인덱스 품질의 문제이지 사용자가 조율할 취향이 아니다. 노브로 열면 "왜 내 검색이 다르지"의 원인이 늘어난다. 바꿔야 하면 코드 기본값을 바꾼다.

7.3구현 시 확정한 두 가지 조정 (Rev 0.2)

Refinement · 구현 결정 초안(Rev 0.1)의 두 지점을 구현하며 더 나은 형태로 확정했다. 목표(원본을 이고 다니지 않는다)는 동일하며, 오히려 더 순수해졌다.
항목초안 0.1확정 0.2이유
원격 수집미러를 잠깐 받았다 삭제ssh export — 미러를 아예 안 만듦매 run마다 삭제하면 rsync 증분이 깨져 15분마다 10GB 재전송. 원격이 digest만 추출해 보내면(sessionhub export --since) 전송이 KB 단위
DIGEST 저장digests/*.txt.zst 파일hub.db 내 blob 테이블 (gzip)세션당 파일 수천 개는 이동·백업을 번거롭게 함. blob은 ~20MB라 여전히 작고 단일 파일로 관리. zstd는 3.14+ 전용이라 zero-dep 위해 gzip

keep_mirror 노브는 사라졌다 — 미러 개념 자체가 없으므로 무의미하다. 남은 노브는 digest.mode 하나. 원격 미도달 시 export는 rsync가 그랬듯 조용히 no-op 하고 아무것도 만들지 않는다.

9.0README에 반영할 것

  • ## How it works 교체 — 5.0의 MIRROR → DIGEST → INDEX 3층 그림 + 층별 한 줄. "원본을 다 이고 가지 않는다. 대화만 정제해 보관하고, 검색은 인덱스로."
  • ## Storage 신규(접이식) — 4.0 실측표(0.3%)와 8.0 용량표, 두 노브의 트레이드오프. 기본값이 왜 B인지 한 문단.
  • 원문 참조 문구 — raw가 전문을 못 열 때 "원본은 <host>:~/.claude/…에 있습니다"를 그대로 출력해, 사용자가 원위치를 안다는 확신을 준다.
